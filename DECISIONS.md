# Решения, принятые там, где ТЗ не даёт ответа

## Сборка и окружение
- **Каркас и версии.** Проект создан `flutter create` на Flutter 3.50 (stable), версии пакетов зафиксированы в `pubspec.lock`. Material-виджеты импортируются из пакета `material_ui` (так устроен текущий stable).
- **Генерируемый код Drift** (`*.g.dart`) в репозиторий не кладётся, генерируется `build_runner` в CI и локально.
- **`flutter analyze --no-fatal-infos`.** Ошибки и предупреждения валят сборку, информационные замечания — нет (в `tables.dart` Drift требует самоссылающихся геттеров для CHECK).
- **Подпись.** Без `android/key.properties` release-сборка подписывается debug-ключом, чтобы CI работал до настройки секретов; GitHub Release создаётся только при наличии ключа.
- **versionCode** = номер запуска workflow (`--build-number`); при сборке по архитектурам Flutter добавляет к нему 1000 × код ABI.
- **APK по архитектурам.** CI собирает `--split-per-abi` и публикует `trainlog-arm64.apk` и `trainlog-arm32.apk`: универсальный APK весил больше 80 МБ. Для каждого файла в лог пишутся размер, SHA-256 и результат `apksigner verify`.
- **Логи CI** дублируются в ветку `ci-logs`.
- **compileSdk = 37**: этого требуют `flutter_local_notifications` 23 и `androidx.core` 1.19; `targetSdk` — по умолчанию Flutter.

## База данных
- **Имена и типы** — по разделу 7 ТЗ. `created_at` / `updated_at` есть во всех таблицах; `updated_at` обновляет триггер SQLite.
- **`recipe_items`, `exercise_muscles`** — составной первичный ключ, отдельного `id` нет.
- **`food_logs.product_id`** допускает NULL с `ON DELETE SET NULL`: удаление продукта не трогает историю (в записи хранится снимок КБЖУ).
- **Удаление упражнения** с записями в журнале или программах запрещено (`ON DELETE RESTRICT`); интерфейс в этом случае архивирует его.
- **Удаление программы** не удаляет журнал: у сессий обнуляются ссылки на план.
- **Служебное состояние** (последняя закрытая неделя, дата напоминания о копии) в схему не добавляется, так как схема ограничена 22 таблицами: оно лежит в файле `app_state.json` рядом с базой.

## Планировщик
- **Шаг округления веса** в ТЗ указан параметром программы, а в схеме лежит в `settings.weight_rounding_kg`. Он один на приложение и редактируется и в форме программы, и в настройках.
- **Дни недели и длина цикла** задаются при создании программы и потом не меняются; название, лимит времени, неделя разгрузки и коэффициенты меняются.
- **Неделя разгрузки** не может быть первой (ей не из чего строиться).
- **Линейный шаг** считается по рабочим неделям: разгрузочная неделя не увеличивает счётчик.
- **Режим «% от 1ПМ»** берёт последний расчётный 1ПМ упражнения из недельной статистики. Пока его нет, вес пустой и задаётся вручную.
- **Вес разгрузки** округляется вниз до шага (как все веса плана); RIR ограничен сверху значением 5.
- **Ручная правка** веса в режимах «%» и «линейный», а также любая правка разгрузочной недели ставит `is_manual`; кнопка «Сбросить» возвращает расчёт.
- **При переносе разгрузки** бывшая разгрузочная неделя получает подходы, повторы и RIR первой рабочей недели.
- **Подсказки при превышении лимита:** «убрать подход» действует на последнее изолирующее упражнение дня во всех рабочих неделях; «сократить отдых» — минус 30 с у всех упражнений дня (не меньше 30 с).

## Журнал
- **Плановые повторы подхода** = нижняя граница диапазона; недобор считается от неё.
- **«По плану»** — одно нажатие: факт = плановые вес и повторы, RIR = целевой.
- **Статус упражнения** — худший из done / minor_miss / partial / failed; пропущенные подходы его не ухудшают, если пропущены все — skipped.
- **Завершение тренировки** помечает невыполненные подходы пропущенными (после подтверждения).
- **Тренировку дня можно начать в любой день недели**; на один день программы в неделе — одна сессия.
- **Разминочные подходы** показываются первыми, статуса и 1ПМ не имеют.
- **Таймер отдыха** хранит момент окончания и планирует точное уведомление (`USE_EXACT_ALARM`); отдых для упражнений без плана — 120 с.

## Аналитика
- **Порог r > 12** применяется к значению, подставляемому в формулу: при включённом учёте RIR это r + RIR.
- **Недельные агрегаты** считаются только по завершённым сессиям; неделя — с понедельника по воскресенье.
- **`e1rm_delta_pct`** — к последней предыдущей неделе, в которой у упражнения есть 1ПМ.
- **Период «Мезоцикл»** — недели активной программы; без неё — последние 12 недель.

## Рекомендации
- **Объект правила** — упражнение в программе (`program_day_exercise`) или программа целиком; на объекте одновременно одна рекомендация в статусе new.
- **TWO_RED_IN_ROW, выбор p.** Статус failed уже означает недобор ≥ 6 хотя бы в одном подходе, поэтому p = 5% берётся, когда во второй сессии недобор ≥ 6 во всех рабочих подходах, иначе 2,5%. Вес — плановый вес следующей сессии; при принятии все будущие недели упражнения уменьшаются на ту же величину и помечаются `is_manual`.
- **E1RM_PLATEAU.** «Не вырос N недель»: максимум 1ПМ за последние N недель (по умолчанию 3) меньше значения перед ними × 1,01; разгрузочные недели в ряд не входят. «+1 подход» добавляется во все будущие рабочие недели.
- **EARLY_DELOAD.** «Без роста 2 недели» считается так же с N = 2; доля жёлтых и красных — по подходам упражнений программы за закрытую неделю. Действие переносит разгрузку на следующую неделю (прежняя разгрузочная неделя становится рабочей), линейная прогрессия сдвигается сама. Не срабатывает, если следующая неделя уже разгрузочная или цикл закончился.
- **Подавление.** Если досрочная разгрузка сработала при этом закрытии недели или следующая неделя разгрузочная, E1RM_PLATEAU не создаётся.
- **Cooldown** отсчитывается от `resolved_at` любой решённой рекомендации этого правила на этом объекте (принята, отклонена, истекла).
- **Истечение.** Рекомендация по упражнению истекает при завершении следующей сессии этого упражнения; по программе — при закрытии следующей недели.
- **Откат** возвращает план по `previous_values` и переводит рекомендацию в «отклонена».
- **Закрытие недели** выполняется при запуске до показа интерфейса. При первом запуске закрывается только прошлая неделя.
- **Пороги правил** редактируются на экране «Правила» (JSON условия и действия, приоритет, пауза, включение).

## Питание
- **Вес для расчёта нормы** — тренд последнего взвешивания (если его нет — сам вес). Без веса, роста или даты рождения норма не считается, экран дня подсказывает заполнить профиль.
- **Норма пересчитывается** при любой правке профиля и сохраняется в `nutrition_targets` с сегодняшней датой; для прошлых дней показывается норма, действовавшая на тот день. Смена активности сбрасывает расход к формульному.
- **Смена цели** подставляет значения по умолчанию: набор +10% и 1,8 г/кг белка, снижение −15% и 2,2 г/кг, удержание 0% и 1,8 г/кг; ползунки ограничены диапазонами ТЗ.
- **`goal_adjust_pct`** хранится положительным числом процентов, знак определяет цель.
- **Тренд веса** пересчитывается целиком при каждой правке веса; `trend_kg` хранится только для дней со взвешиванием, пропуски интерполируются при расчёте.
- **Open Food Facts.** Название берётся из `product_name_ru`, если оно есть, иначе из `product_name`. Карточки без `energy-kcal_100g` в поиске не показываются; при сканировании такой карточки открывается ручной ввод с подставленным штрихкодом. Сканер включён в этап «Питание».
- **Правка граммов записи** пропорционально пересчитывает её снимок КБЖУ, а не берёт текущие значения продукта.
- **Удаление записи** — смахиванием влево; удаление веса дня — долгим нажатием на карточку веса.

## Открытые вопросы ТЗ
- Сканер штрихкода камерой сделан в этапе «Питание».
- Недобор 1–2 — «зелёный с меткой» (как принято в ТЗ).
- Подходы на время и с собственным весом отдельно не учитываются: вес 0 кг допустим, 1ПМ для него не считается.
